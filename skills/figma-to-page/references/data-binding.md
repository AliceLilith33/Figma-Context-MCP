# 数据层与字段绑定规则

## 1. 设计元素 → 接口字段的匹配依据（按可靠程度排序）

1. **示例值吻合**：设计稿里的占位值和字段的 `e.g.` 示例格式一致（`¥128.00` 对 `amount  # e.g. 12800`）。
2. **字段说明吻合**：设计稿文字和字段 `#` 后的说明一致或近义（「下单时间」对 `createdAt  # 下单时间`）。
3. **字段名吻合**：图层名或文字的英文含义和字段名一致（`OrderNo` 图层对 `orderNo`）。
4. **结构吻合**：重复结构（`template=`）对数组字段，重复次数不重要。
5. **仅凭位置或常识猜测**：必须在对照表里标「猜测」。

**容易混淆的字段**（实付/应付/原价金额，创建/支付/更新时间，昵称/姓名/账号）必须用第 1、2 条的依据区分。区分不了的，在对照表里列出所有候选，交给人决定。

## 2. 类型

- 优先用项目的 OpenAPI 代码生成（见约定文档）。生成的类型和 `get_api_context` 的结构不一致时，以生成的类型为准。
- 没有代码生成时，按 `get_api_context` 的 `detail=full` 结果手写类型。注意：
  - 字段带 `?` 表示可选。**整个 schema 都没有 `?` 不代表都必填**，可能只是文档没写 `required`，访问嵌套字段时做好空值保护。
  - `| null` 要写进类型。
  - `string<int64>` 或 `integer<int64>` 可能超出 JS 的数值精度，按字符串处理。
- 交付时注明类型是生成的还是手写的。

## 3. 请求函数

- 只能通过约定里的请求封装发请求。函数名和 operationId 保持一致（`listOrders`），方便追溯。
- 路径参数、查询参数、请求体都按 `params`/`body` 的定义写。`bodyType` 不是 JSON 时（表单、multipart），按对应格式编码。
- 统一返回包装（`{ code, data, msg }`）：如果拦截器已经解包，函数直接返回 `data` 的类型，不要重复解包。

## 4. 数据转换（只在显示层做，不改原始数据）

| 场景     | 规则                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------- |
| 金额     | 先看字段说明里的单位（分还是元），用约定里的格式化函数。说明里没写单位的，在对照表里标出       |
| 时间     | `string<date-time>` 或 `string<date>` 用约定里的工具函数格式化，格式以设计稿为准               |
| 枚举     | 枚举值和显示文案的对应关系放在约定的常量文件里，不要写在组件中。设计稿里的文案就是对应的显示值 |
| 分页     | 按约定的参数名转换。总数字段用于分页组件                                                       |
| 图片 URL | 接口返回的图片地址直接使用。设计稿里下载的示例图只能作为占位或兜底                             |
| 空值     | 用约定的占位符（如 `-`），不要显示 `undefined`/`null`                                          |

## 5. 写操作

- 提交前在客户端做必填校验，规则来自 `body` 中不带 `?` 的字段。前提是 `body` 里至少有一个字段带 `?`（说明文档写了 `required`）；一个都没有时无法判断，按设计稿的必填标记（如红色星号）校验，并在交付时说明。
- 成功后的行为（刷新列表、跳转、提示）以设计稿或约定为准。设计稿里没有的，选最保守的做法（提示并刷新当前数据），并在交付时说明。
- 所有写操作都要列进交付的「写操作表」。
