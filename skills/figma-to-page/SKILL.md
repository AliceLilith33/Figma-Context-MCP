# Figma 设计稿 → 对接接口的页面

## 前提（开始前检查，缺了就停下告诉用户）

- Framelink MCP 可用（能看到 `get_api_context` 工具）。只做静态还原时可以没有。接口文档不必在服务配置里指定，按第 2 步「确定接口文档」处理。
- Figma 账号是付费计划的 Dev/Full 席位。其他席位的 Tier 1 调用按月计、额度极少，本流程会很快耗尽。
- 视觉对比（第 1 步）和验收（第 6 步）需要 chrome-devtools MCP。没有就跳过这两处的浏览器部分，并在交付时说明。

## 硬性规则

- **项目约定优先**：先读 `docs/frontend-conventions.md`。不存在则执行第 0 步。约定与本文件冲突时以约定为准。
- **一次只做一个页面或区块**。设计稿过大时先用 `depth` 取上层结构，再按区块取（`get_figma_data` 的说明要求用户明确要求才用 `depth`，本条即视为用户的要求）。
- **参考图只渲染一次**，存在 `.figma-ref/`，后续复用。Figma 调用有配额。
- **不新增依赖**，除非约定允许，或用户同意（MSW、pixelmatch 都属于这一类）。
- **写操作不在真实后端上执行**：验收时不点击提交、删除、支付等会产生副作用的按钮，除非用户明确说明当前是可随意写入的环境。
- **修复最多 2 轮**：验收不通过 → 修 → 再验，2 轮后仍有问题就列出来交给人。

## 分阶段执行

流程分为两个阶段，可以在同一次会话里连续完成，也可以分开做（中间可以隔几天、换会话或换人）。

| 阶段           | 步骤           | 什么时候只做这一段                                           | 需要的工具                            |
| -------------- | -------------- | ------------------------------------------------------------ | ------------------------------------- |
| **A 静态页面** | 0 → 1 → A 交付 | 用户说"先做静态页面""接口还没好"，或者没有 `get_api_context` | get_figma_data、download_figma_images |
| **B 对接接口** | 2 → 7          | 用户说"把 xx 页面接上接口"，且页面已经存在                   | get_api_context（不需要再取设计稿）   |

用户没有说明时：`get_api_context` 可用、且能确定接口文档（见第 2 步）就连续做 A 和 B；否则只做 A，并告诉用户之后怎么接着做 B。

**两个阶段之间靠「交接文件」衔接**：阶段 A 生成，阶段 B 读取，格式见下面第 1 步。阶段 B 有了交接文件，就不需要再调用 `get_figma_data`（节省 Figma 配额）。

## 流程

### 0. 项目约定（仅首次）

`docs/frontend-conventions.md` 不存在时：读代码库（package.json、请求封装、已有页面、组件库、路由、格式化工具），按 [references/conventions-template.md](references/conventions-template.md) 起草这份文件，**交给用户确认后**再继续。确认后在 CLAUDE.md 里加一行指向它。

### 1. 静态还原 + 视觉对比

1. 用 `get_figma_data` 获取设计稿。
2. 用 `download_figma_images` 下载其中用到的图片和图标，**同一次调用里**渲染整页参考图（省一次 Figma 调用），方法见 [references/figma-reference.md](references/figma-reference.md)。
3. 用设计稿里的**占位内容**写出静态页面，复用已有组件。**将来由接口提供的内容**（订单号、金额、列表项、用户名、状态等）全部放进交接文件，不能写死在模板中，方便第 4 步整体替换。固定的界面文案（页面标题、按钮文字、表头）留在模板里。拿不准的放进交接文件，并在注释中标明。
4. **视觉对比只在这一步做**：此时页面内容和设计稿一致，对比才有意义。方法见 [references/verification.md](references/verification.md) 的「静态阶段」。

**交接文件**：放在页面旁边，命名为 `<页面文件名>.mock.ts`（JS 项目用 `.mock.js`），**提交到仓库**，不要放进 `.figma-ref/`，因为阶段 B 可能由别人在别的机器上做。文件头部用注释记录阶段 B 需要的设计信息：

```ts
/**
 * @figma     https://www.figma.com/design/AbC123/Shop?node-id=12-345
 * @keywords  我的订单, 实付金额, 下单时间, 收货人, 待支付, 已支付, 已发货, 查看详情, OrderCard
 * @lists     orders ← OrderCard（template=EL-3f9a2c1b，重复 3 次）
 * @actions   查看详情 → 跳转详情页；状态筛选标签 → 列表过滤
 * @stage     static        （阶段 B 完成后删除本文件）
 */
export const MOCK_ORDERS = [
  {
    id: "202501020001",
    amount: "¥128.00",
    createdAt: "2025-01-02 10:00",
    buyerName: "张三",
    status: "待支付",
  },
];
```

- `@keywords`：设计稿中的可见文字和语义化图层名，供阶段 B 检索接口用。
- `@lists`：重复结构对应哪个 mock 数组，阶段 B 据此匹配数组字段。
- `@actions`：按钮、表单、筛选等交互，阶段 B 据此找写接口和查询参数。

**阶段 A 交付**（只做阶段 A 时）：改动文件列表、交接文件路径、视觉对比结果，以及下一步怎么做，例如："接口就绪后说「把订单列表页接上接口」"。

### 2. 找接口

**先确定接口文档**（OpenAPI 3.x 或 Swagger 2.0），按顺序找，找到就停：

1. 用户在对话里给出的文件或地址。
2. 约定文档「接口文档」一节记录的位置。
3. 服务配置的默认文档：`get_api_context` 的工具说明里写着 `configured spec (<位置>)`，就用它，调用时不带 `spec`。
4. 在项目里找 `openapi.*`、`swagger.*`、`api-docs*.json` 这类文件，打开确认是接口文档（有 `openapi:` 或 `swagger:` 字段）。
5. 都没有就**问用户**，不要猜。提示用户可以给一个导出的单文件（如 `swagger.json`、`openapi.yaml`），或者文档本身的 URL（如 `/v3/api-docs`，不是 Swagger UI 页面）。

注意：

- `spec` 传**绝对路径**（项目内的文件就用项目根目录拼出来）或 URL。之后**每次**调用 `get_api_context` 都带上同一个 `spec`，服务端不会记住。
- 新确定的位置写进约定文档的「接口文档」一节（项目内的文件写相对路径），下次直接用。用的是服务的默认文档时写「服务配置的默认文档」，不要抄工具说明里的地址：那里去掉了查询参数，可能少了令牌。
- 工具返回的错误会说明原因：给的是 HTML 页面、Postman 导出文件、目录、相对路径等。按提示处理，需要用户重新导出的就告诉用户。
- 结果里有 `warning` 说文档拆成了多个文件时，被引用的部分显示为 `unresolved(...)`。请用户给一个合并后的单文件，不要根据 `unresolved` 的名字猜字段。

**再找接口**：

1. 收集关键词：
   - **有交接文件**：直接用其中的 `@keywords`、`@lists`、`@actions`，不要再调用 `get_figma_data`。
   - **没有交接文件**（页面不是用本 Skill 做的）：向用户要 Figma 链接，调用 `get_figma_data`，收集可见文字（标题、标签、按钮、状态、占位值）、语义化的图层名、重复结构（带 `template=` 的节点，对应 ELEMENTS 段，通常意味着列表和数组字段）。同时找出页面中写死的占位内容，第 4 步要替换掉。
2. 调用 `get_api_context(spec, keywords)` 得到候选接口。结合 `matched` 字段和接口 summary 判断，选出页面需要的读接口和写接口。
3. 对选中的接口调用 `get_api_context(spec, operationIds)`，取完整结构。

### 3. 数据层

按 [references/data-binding.md](references/data-binding.md) 实现：

- 类型的来源：项目有 OpenAPI 代码生成就用生成的类型，没有才手写（交付时注明）。`get_api_context` 返回的结构是简化过的，不能作为类型的唯一依据。
- 请求函数用项目的请求封装，再按项目惯用方式封装成数据 hook 或 store。
- 处理统一返回包装、分页、金额/时间/枚举转换。

### 4. 绑定数据

把页面中对交接文件（或写死的占位内容）的引用换成真实数据。按钮和表单接上写接口。补齐 loading、空数据、错误三种状态，设计稿没画的状态用项目已有的通用组件。

替换时顺手记下每处「占位值 → 字段」（如 `¥128.00 → amount`），这是第 7 步字段对照表的依据。全部替换完成后，**删除交接文件**，并确认没有任何地方还在引用它。验收用的模拟数据由 MSW 提供（见第 6 步），不再需要它。

### 5. 运行检查

运行项目的类型检查和 lint（命令见约定文档），全部通过后再进入验收。

### 6. 验收

按 [references/verification.md](references/verification.md) 的「数据阶段」执行。后端模式按下面的规则选：

| 模式                         | 什么时候用                                 | 能验证什么                                         |
| ---------------------------- | ------------------------------------------ | -------------------------------------------------- |
| **mock**（MSW）              | 默认；后端没有就绪；需要测空数据、错误状态 | 正常、空数据、错误、加载中四种状态都能稳定触发     |
| **live**（真实开发环境后端） | 用户要求联调，且提供了地址和测试账号       | 真实的请求、鉴权和数据；只看正常数据，不执行写操作 |

用户要求"两种都测"时，先跑 mock，再跑 live。

### 7. 交付

输出以下内容，不用写过程描述：

1. **改动文件列表**
2. **字段对照表**：UI 元素 | 接口 | 字段 | 依据（命中的关键词、字段名或示例值）| 备注。依据必须具体，不能写"语义相近"。
3. **写操作表**：按钮或表单 | 接口 | 参数来源，**请用户确认**。
4. **未匹配项**：设计稿中找不到对应字段的元素，以及接口中有但页面没用到、可能需要展示的字段。
5. **验收结果**：每项注明通过、不通过或跳过（附原因），类型是否为手写。
